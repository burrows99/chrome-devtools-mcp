# Heap Snapshot Manager

> **Layer:** Performance & memory engine · **Sources:** `src/HeapSnapshotManager.ts`, `src/utils/id.ts` · **Verified at:** commit afa5622 (2026-06-19)

## Purpose
Load `.heapsnapshot` files into the vendored DevTools heap-snapshot worker, cache the resulting proxies per file path, and expose typed queries — aggregates, statistics, nodes-by-class, retainers, retaining paths, dominators, and outgoing edges. This is first-party glue around the vendored `HeapSnapshotModel` proxy API.

## Key files
- `src/HeapSnapshotManager.ts` — the manager class.
- `src/utils/id.ts` — `createIdGenerator`, `stableIdSymbol`, `WithSymbolId<T>` helpers used to attach small stable ids to aggregates.

## Key types & functions
- `HeapSnapshotManager` — owns a private `#snapshots` map keyed by absolute file path.
- `AggregatedInfoWithId` — `WithSymbolId<DevTools...AggregatedInfo>`; a vendored aggregate decorated with a `[stableIdSymbol]` number.
- `getSnapshot(filePath)` — returns a cached `HeapSnapshotProxy` or loads one via `#loadSnapshot`.
- `getAggregates(filePath)` — `Record<classKey, AggregatedInfoWithId>` from `snapshot.aggregatesWithFilter(new NodeFilter())`; each aggregate is tagged with a small stable id.
- `getStats(filePath)` — `snapshot.getStatistics()`.
- `getStaticData(filePath)` — `snapshot.staticData`.
- `getNodesById(filePath, id)` — resolves the class key from the small id, then `createNodesProviderForClass(className, filter).serializeItemsRange(0, Infinity)`.
- `getRetainers(filePath, nodeId)` — `createRetainingEdgesProvider(nodeIndex).serializeItemsRange(0, Infinity)`.
- `getRetainingPaths(filePath, nodeId, maxDepth?, maxNodes?, maxSiblings?)` — `snapshot.getRetainingPaths(...)`.
- `getDominatorsOf(filePath, nodeId)` — `snapshot.getDominatorsOf(nodeIndex)`.
- `getEdges(filePath, nodeId)` — `createEdgesProvider(nodeIndex).serializeItemsRange(0, Infinity)`.
- `getOrCreateIdForClassKey` / `resolveClassKeyFromId` — the two-way small-id ↔ class-key mapping.
- `hasSnapshots()` / `dispose(filePath)` — lifecycle: report whether any are loaded; tear one down (disposes its worker, deletes the cache entry).

## How it works
**Caching (first-party).** `#snapshots` maps `path.resolve(filePath)` to `{ snapshot, worker, idToClassKey, classKeyToId, idGenerator }`. The first `getSnapshot` for a path loads it; subsequent calls reuse the proxy. Every query method funnels through `getSnapshot`, so it lazily loads on demand.

**Loading via a worker (first-party glue around vendored proxy).** `#loadSnapshot`:
1. Creates a vendored `HeapSnapshotWorkerProxy`, pointing it at the worker entrypoint resolved with `import.meta.resolve('./third_party/devtools-heap-snapshot-worker.js')`.
2. Uses `Promise.withResolvers()` to get a promise that resolves when the loader callback fires with the finished `HeapSnapshotProxy`.
3. Streams the file from disk (`fs.createReadStream`, 1 MB `highWaterMark`, utf-8), writing each chunk into `loaderProxy.write(chunk)`, then `loaderProxy.close()`.
4. Awaits the snapshot promise and returns `{snapshot, worker}`.

**Two id spaces — important.** There are two distinct id concepts:
- The vendored snapshot's own `nodeId` (used by retainers/paths/dominators/edges, resolved to a `nodeIndex` via `snapshot.nodeIndexForId(nodeId)`).
- A small **stable class id** generated by this manager (`createIdGenerator`, counts from 1) and mapped to/from the verbose `classKey` string. `getAggregates` tags each aggregate with this id via `stableIdSymbol`; `getNodesById` accepts that small id and resolves it back to a class key. This keeps class identifiers short and stable across paginated tool calls.

```ts
// id.ts — small incrementing ids, wraps at MAX_SAFE_INTEGER
export function createIdGenerator() { let i = 1; return () => { if (i === Number.MAX_SAFE_INTEGER) i = 0; return i++; }; }
export const stableIdSymbol = Symbol('stableIdSymbol');
```

**Serialization.** Node/edge/retainer providers are serialized eagerly over the full range `serializeItemsRange(0, Infinity)`; pagination happens later in the formatter/response layer, not here.

## Gotchas & non-obvious details
- **Each snapshot owns a live worker.** Loading a snapshot spawns a worker proxy that stays alive until `dispose(filePath)` (driven by the `close_heapsnapshot` tool). Forgetting to close leaks the worker.
- **Paths are normalized.** All map keys go through `path.resolve`, so relative and absolute paths to the same file share one cache entry.
- **`getOrCreateIdForClassKey` is `async` but does no I/O** — it only touches in-memory maps; the `async` is for interface symmetry.
- `#getCachedSnapshot` throws `Snapshot not loaded for ...` if a class-key/id helper is called before the snapshot was loaded.
- Streaming with a 1 MB chunk size keeps large snapshots off the heap during load.

## Update triggers
- `chrome-devtools-frontend` version bump changes the `HeapSnapshotModel` proxy API or `AggregatedInfo` shape.
- The worker entrypoint path (`./third_party/devtools-heap-snapshot-worker.js`) moves or its build output changes.
