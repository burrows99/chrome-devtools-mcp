# Architecture & request lifecycle

> **Layer:** System overview · **Sources:** `src/index.ts`, `src/ToolHandler.ts`, `src/McpContext.ts`, `src/browser.ts` · **Verified at:** commit afa5622 (2026-06-19)

## Purpose
Explain how the layers fit together and trace one tool call end to end. For the
authoritative detail of any box below, follow its link.

## The stack (high → low)
```
MCP client (agent)
   │  MCP protocol over stdio
   ▼
Entrypoint / MCP server         ── src/bin/*, src/index.ts        → 01-entrypoints
   │  registers tools, routes calls
   ▼
Tool system                     ── src/tools/*, src/ToolHandler   → 02-tools
   │  validates args, runs handler
   ▼
Context & state                 ── McpContext / McpPage / McpResponse → 03-context-state
   │  owns pages, collectors, snapshots, emulation state
   ▼
Browser & CDP                   ── src/browser.ts, src/devtools/* → 04-browser-cdp
   │  Puppeteer + CDP sessions + vendored host bindings
   ▼
Chrome (live browser)
```
Cross-cutting layers, used by many of the above:
- **Formatters** ([05](../05-formatters/README.md)) — turn collected data into token-efficient output.
- **Performance & memory engine** ([06](../06-performance-memory/README.md)) — trace parsing + heap analysis (mostly vendored).
- **Telemetry & logging** ([07](../07-telemetry/README.md)) — Clearcut metrics + debug logger.
- **Utilities** ([08](../08-utilities/README.md)) — small shared helpers + types.

## Lifecycle of one tool call
1. **Receive** — the MCP server (`src/index.ts`) hands an incoming tool call to the
   dispatcher in [`ToolHandler`](../02-tools/tool-handler.md).
2. **Validate** — the tool's Zod schema (declared in its [`ToolDefinition`](../02-tools/tool-definition.md))
   validates/parses the arguments.
3. **Serialize access** — the handler runs against the shared
   [`McpContext`](../03-context-state/mcp-context.md), typically guarded by a
   [`Mutex`](../03-context-state/concurrency.md) so browser actions don't interleave.
4. **Act** — the handler drives Chrome through
   [`McpPage`](../03-context-state/mcp-page.md) / Puppeteer / CDP
   ([browser & CDP](../04-browser-cdp/README.md)).
5. **Collect** — console/network/issue/service-worker data is captured by
   [collectors](../03-context-state/collectors.md) attached to the page.
6. **Format** — results are rendered by a [formatter](../05-formatters/README.md)
   and assembled into an [`McpResponse`](../03-context-state/mcp-response.md)
   (text + optional structured content; heavy assets returned by reference).
7. **Record** — the call outcome is logged to [telemetry](../07-telemetry/README.md).
8. **Return** — the response goes back over MCP to the agent.

## Two big architectural facts
- **`McpContext` is the hub.** Graph analysis of this repo shows `McpContext`
  bridging ~16 subsystems — it is the single most-connected abstraction. Changes
  there ripple widely. See [mcp-context.md](../03-context-state/mcp-context.md).
- **A large vendored bundle.** Trace/Lighthouse processing relies on a vendored,
  minified `chrome-devtools-frontend` / `lighthouse` bundle regenerated by
  `scripts/update-lighthouse.ts`. Treat it as an opaque dependency, not
  first-party code. See [lighthouse-vendoring](../09-build-tooling/lighthouse-vendoring.md).

## Update triggers
- A new layer/subsystem is introduced, or the tool-call lifecycle changes (e.g.
  new validation, new response envelope).
